## 2. Canonical Verification Rule

```text
Verify(x) = clear_for_routing
iff x carries:
  Layer
  Source
  Receipt
  BoundaryStatus
```

Expanded:

```text
Layer := taxonomic namespace or claim layer
Source := origin of the payload or assertion
Receipt := commit SHA, path, screenshot witness, explicit user-provided capsule, or other traceable ledger marker
BoundaryStatus := retrieved / reconstructed / inferred / symbolic / speculative / unverified
```

A promoted structural assertion must identify its layer, source, receipt, and boundary status.

This does not mean every creative or exploratory token is rejected. It means only verified structures are promoted to canon, routed as stable architecture, or written forward as durable state.

## 3. Verification Gates

### Gate 1 — Layer Check

Confirms the payload's structural namespace.

Valid examples:

```text
Ξ.Thread
Ξ.Capsule
Ξ.Frame
Ξ.Route
Ξ.Agent
Ξ.Runtime
Ξ.Lexicon

```

The Layer Check prevents low-dimensional name-clustering, identity overlap, and accidental category collapse.

### Gate 2 — Source Check

Confirms the origin of the payload.

Valid source classes:

```text
Git hard anchor
active conversation context
uploaded witness artifact
screenshot witness layer
explicit user-provided capsule
prior committed registry file
external node response marked as witness, not objective execution
model inference marked as inference
```

### Gate 3 — Receipt Check

Confirms that the payload has a traceable marker.

Valid receipt classes:

```text
commit SHA
repository path
timestamped exported capsule
file name / upload reference
quoted user payload
explicit routeable anchor
screenshot batch marker
```

### Gate 4 — Boundary Status Check

Confirms the payload states what kind of truth it carries.

```text
retrieved      := read from a tool, file, or ledger
reconstructed := rebuilt from capsules / summaries / active context
inferred       := derived from pattern relations, not directly retrieved
symbolic       := meaningful glyphic or mythic layer, not empirical claim
speculative    := possible architecture or hypothesis, not verified fact
unverified     := observed but not yet receipt-bound
```

## 4. Verification Output States

```text
PASS:
  route payload forward
  preserve confidence
  no unnecessary threshold relitigation

SOFT_FAULT:
  hold payload in witness layer
  request or locate missing receipt
  do not discard useful structure

HARD_FAULT:
  block canon promotion
  quarantine from routing
  preserve as anomaly if useful

DOOR:
  hallucination / anomaly / drift signal detected
  classify as symbolic, speculative, or inferred
  keep if useful
  prevent false factual promotion
```
